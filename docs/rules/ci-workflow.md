# GitHub Actions ワークフローのルール

`.github/workflows/` を編集するときに守ること。レビューで繰り返し指摘された内容をまとめる。

## 式展開をシェルに直接埋め込まない

`run:` の中に `${{ ... }}` を直接書かない。値は `env:` に渡し、シェル側では
`"$VAR"`（PowerShell では `$env:VAR`）で参照する。式の中身が展開後にそのまま
シェルへ渡るため、スクリプトインジェクションの入口になる。

```yaml
# ✅ Good
- env:
    RELEASE_TAG: ${{ github.event.release.tag_name }}
  run: echo "$RELEASE_TAG"

# ❌ Bad
- run: echo "${{ github.event.release.tag_name }}"
```

`uses:` の `with:` はシェルを経由しないので、そのまま `${{ }}` を書いてよい。

## permissions は最小権限にする

トップレベルは `contents: read` にし、書き込みが必要なジョブにだけ
`permissions: contents: write` を付ける。リリース資産を書き換えられるトークンを、
依存パッケージのライフサイクルスクリプト（`npm ci` の postinstall など）が動く
ジョブ全体に配らない。

## 成果物のアップロードは「無いときに失敗する」形にする

`for file in dist/*.zip; do if [ -f "$file" ]; ...` のようなループは、成果物が
1 つも無いときに何もせず成功する。パスを一意に確定して指定し、存在しなければ
ステップが落ちるようにする。PowerShell のループでは `$LASTEXITCODE` が最後の
コマンドの値しか持たないため、各反復で明示的に判定する。

## 検証は成果物のアップロードより前に置く

署名・公証などの検証ステップはアップロードステップより前に置く。
`continue-on-error` や `if:` で握り潰さない（後続はデフォルトの `success()` で
skip されるので、検証が落ちれば成果物は出ない）。

## bash スクリプトは前提を明示する

複数行の `run:` では `shell: bash` を明示し、先頭に `set -euo pipefail` を置く。
デフォルトの `bash -e` には `pipefail` が無く、後からパイプを足したときに失敗が
握り潰される。

クリーンアップは `trap ... EXIT` で行い、まだ実行していない後始末を走らせないよう
フラグで守る（例: マウント前に detach しない）。EXIT トラップはハンドラ内で
`exit` を呼ばない限り元の終了ステータスを保持するので、`|| true` を付けても
検証の失敗は伝播する。

## 同じパスを複数のステップに書かない

成果物のパスのようにステップをまたいで使う値は、`$GITHUB_OUTPUT` に出す
ステップを 1 つ作り、以降はそれを参照する。命名規則を変えたときの追従漏れは
リリース本番でしか顕在化しない。
